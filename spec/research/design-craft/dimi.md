## Shipped from earlier code tricks (this session, before this folder existed)

Two of dimi's patterns were already evaluated, adapted, and shipped as real components before `spec/research/design-craft/` was set up — recorded here for completeness rather than in a fresh note, since the actual implementation and reasoning live in the code and commit history, not a separate essay.

- **`src/components/ui/shared-layout-background.tsx`** — adapted from dimi's ["Shared Layout Background"](https://www.dimi.me/lab/shared-layout-background) (Radix + Motion `layoutId` hover-highlight that moves between list items, fading only at the group boundary). Adapted for Base UI (no `asChild`, uses `render` instead), given a `render` prop so it can host the real semantic list container instead of wrapping it in an extra `div` (would've broken `<ul>`/`<li>` semantics), and given a `data-shared-layout-item` marker so the primitives it wraps (`NavigationMenuTrigger`, `NavigationMenuLink`) can suppress their own competing hover fill via `in-data-shared-layout-item:` variants, rather than each call site overriding classes by hand.
- **`src/components/ui/switch.tsx`** press/disabled feedback — adapted from dimi's ["Animated Switch"](https://www.dimi.me/lab/animated-switch) (Radix + Motion switch with press-scale and a disabled-press shake). Adapted for Base UI's translate-based thumb positioning (Base UI's own canonical demo doesn't use the flex-`justify-content` repositioning the original relied on), rewritten to trigger the shake via a direct `animate()` call in `onPointerDown` instead of the original's `useEffect`-watching-a-state-flag pattern (a real anti-pattern this project's `no-useEffect` skill explicitly bans), and using this project's own established `0.96` press-scale value instead of the source's `0.9`.

Both are useful reference points for a recurring question in this research folder: what does *adapting* a trick well actually look like, versus copying it. Neither was ported as-is.

## github.com/dimicx/animationsdev-hero

<https://github.com/dimicx/animationsdev-hero>

Source for the animated hero on animations.dev (Emil Kowalski's course site) — an SVG scene of several small interactive vignettes (a bouncing/draggable ball, a click interaction, a clock, a code block, a lightbulb, an interactive "timeline" gear) composed together in `scene.tsx`. This is advanced, production-grade marketing-piece code, not a typical UI primitive — not a default pattern for Reway, but several techniques inside it are worth retaining for a future interaction that earns this level of complexity.

Read `scene.tsx` and `bounce.tsx` in full; `timeline.tsx` and the rest (`click.tsx`, `clock.tsx`, `code.tsx`, `lightbulb.tsx`, `defs.tsx`) by structure/summary only.

**Techniques worth remembering:**

- **`useAnimate` + data-attribute selector targeting, at production scale.** `bounce.tsx` drives a whole cluster of SVG elements (`[data-animate='ball']`, `[data-animate='path']`, `[data-animate='bubbles'][data-index='0']`, etc.) through named variant states (`initial`/`hover`/`click`) via a custom `useAnimateVariant` wrapper hook. This is a real, working implementation of the exact `useAnimate` pattern described in Guri's Framer Motion Timeline Guide — worth pointing at this file directly if that pattern ever gets built here for real, rather than starting from the guide's simpler example.
- **`useMotionTemplate` to combine multiple animated transform components into one `transform` string.** The ball's position and squash/stretch scale are each separate `useTransform`-derived motion values (`translateX`, `translateY`, `ballScaleX`, `ballScaleY`), combined via `` useMotionTemplate`translate(${translateX}px, ${translateY}px) scale(${ballScaleX}, ${ballScaleY})` `` into a single `transform`. This is the canonical answer to a real question this project ran into during `switch.tsx`'s press-feedback work: how do you animate *both* position and scale on the *same* element without Motion's internally-built transform string fighting a separately-set one. `switch.tsx` sidestepped the question by putting position and scale on two different nested elements; this shows the alternative — combine them explicitly into one motion-owned `transform` — for a case where splitting into two elements isn't an option.
- **Idle/ambient motion via a dedicated `useAmbientAnimations` hook** — continuous, slow "floating" and "rotation" animations applied to static-looking elements even when nothing is being interacted with, so the scene reads as alive rather than frozen between interactions. Not covered by any other source in this folder. Explicitly gated behind `useReducedMotion` like everything else in the file.
- **Delay-gated hover via a `useHoverTimeout` hook** (a `UNIVERSAL_DELAY` constant applied before a hover-triggered animation starts) — the same "delay before first trigger" principle already established for tooltips (`tooltip.tsx`'s `delay`/`closeDelay`), generalized here to gate any hover-triggered animation, not just tooltip visibility.
- **A `forwardCompleted` ref flag gates whether a click is allowed to advance the sequence** (the ball only cycles its color on click once the preceding hover-triggered bounce animation has actually finished) — implemented entirely with refs and callbacks, no `useState`/`useEffect` anywhere in the sequencing logic. Consistent with, and a more advanced version of, this project's own `no-useEffect` discipline: even the *state* of "has this animation finished" is kept out of React state entirely, since nothing here needs a re-render, only a gate on the next imperative call.
- **Explicit animation cleanup discipline**: a `stopAllAnimations` callback stops every in-flight animation before starting a new one (preventing overlapping conflicting animations on the same elements), and defers the actual `.stop()` calls via `requestIdleCallback` when there are more than 10 running, so cleanup itself doesn't block the main thread. A concrete, code-level example of the "interruptible, tolerate spamming" robustness bar from Rauno Freiberg's Next.js Dev Tools writeup, applied to a scenario (rapid hover in/out) that would otherwise stack up conflicting animations fast.
- **Drag with proportional-follow secondary elements**: dragging the main ball also moves two smaller "bubble" elements, each at a smaller scale factor of the same drag offset (`MAIN_BUBBLE_SCALE`, `MEDIUM_BUBBLE_SCALE`, `SMALL_BUBBLE_SCALE`) — smaller/further elements move less, in proportion to their apparent size. A concrete implementation of "parallax," and a nice physically-consistent detail: the elements don't just move together identically, they move like they have different apparent mass/distance.
