# Design Craft Research — Synthesis

Preserves the reasoning behind eight sources' worth of design-craft research (`emil-kowalski.md`, `rauno-freiberg.md`, `guri.md`, `raphael-salaja.md`, `shu-ding.md`, `dimi.md`, `michael-sommer.md`, `jakub-krehel.md`). Same rule as the design-language synthesis before it: **this is a research record, not a locked decision.** Nothing here is binding until it's written into a skill, `CLAUDE.md`, or a component file as a deliberate, separate step.

Three parts: cross-cutting principles confirmed by two or more independent sources (the actual synthesis), things worth fixing or verifying in code that already exists, and ideas worth keeping in mind for later — not urgent, nothing currently needs them.

The genuinely new, general-purpose material from this batch (not already owned by `make-interfaces-feel-better` or `emil-design-eng`) has since been distilled into the `interaction-craft` skill — marked inline below with **→ `interaction-craft`** wherever an item moved from "research note" to "active skill content." Codebase-specific items (a caveat about one component, a decision still pending) stay here; they don't belong in a general skill.

## Part 1 — Cross-cutting principles (independently confirmed, not just asserted once)

- **The best animation is no animation, especially at high frequency.** Stated independently by Emil Kowalski (twice), Rauno Freiberg, Jakub Krehel (with a sharper quantified framing: a 200x/day animation wastes 6+ hours/year in aggregate), and Shu Ding. The most heavily corroborated single idea across all eight sources.
- **Springs for motion the user is directly driving; fixed duration + easing for motion the system announces.** Raphael Salaja's framing is the sharpest: *"is this motion reacting to the user, or is it the system speaking?"* Guri states the same split independently. **Correction (2026-07-18): an earlier draft claimed this was "checked against every spring/duration choice actually shipped this session," citing `tabs.tsx`, `shared-layout-background.tsx`, and `switch.tsx` press feedback as spring-based examples — none of the three hold up (`tabs.tsx` and `switch.tsx` are plain CSS transitions; `shared-layout-background.tsx` doesn't exist, reverted before this file was written).** Dialogs/sheets genuinely are duration-based. The principle itself remains the most corroborated single idea in this research batch (Guri and Rauno Freiberg state it independently too) — it just isn't demonstrated by real spring usage in this codebase yet.
- **Taste is a trained skill, not innate preference.** Emil Kowalski (two posts), Raphael Salaja (via Hume/Kant/Bourdieu), and Shu Ding's "good design" post (trend-chasing as manufactured dissatisfaction with functional work) all converge here independently.
- **Codify judgment into an agent-readable skill file, don't rely on memory or repetition.** Emil Kowalski ("Agents with Taste") and Jakub Krehel (his own `/codebase-standards` skill, "Less Is More") both arrived here independently — and it's the exact mechanism this project already uses (`make-interfaces-feel-better`, `emil-design-eng`, `CLAUDE.md`). See Part 4 below for what to actually do with this.
- **Sequence which *part* of a multi-step interaction animates first — don't animate everything at once.** Raphael Salaja's Disney "Staging" principle and Rauno Freiberg's "Depth" post (iOS Home Screen: blur → suggestions → keyboard) describe the identical rule with different examples. **→ `interaction-craft`** ("Staging multi-step interactions").
- **Fitts's Law: expand small hit targets via pseudo-elements.** Raphael Salaja names the law formally for a technique already shipped this session — verified citation (corrected 2026-07-18): `button.tsx`, `toggle.tsx`, `select.tsx`, `combobox.tsx`, `sidebar.tsx`, `number-field.tsx`, `autocomplete.tsx`, and `badge.tsx`'s `pointer-coarse:after:` pattern, not `checkbox.tsx`/`switch.tsx`/`radio-group.tsx` as an earlier draft claimed. Rauno Freiberg's prototype writeup describes a *different* technique for the same law (sibling structure instead of a pseudo-element) — see Part 2. **→ `interaction-craft`** (UX laws table), the sibling-technique nuance included.
- **CSS cannot animate to/from `auto` height or width — measuring + animating is required.** Raphael Salaja ("Animating Container Bounds," `useMeasure`+`ResizeObserver`) and Shu Ding ("On UI Animations") state this independently, arriving at the same general solution shape. **→ `interaction-craft`** ("Animating things CSS can't animate on its own").
- **Trend-chasing is a trap; timeless fundamentals compound.** Raphael Salaja and Shu Ding both make this explicit. Matches this project's own existing stance (`feedback_avoid-v1-anchoring` memory, `CLAUDE.md`'s anti-hype rules) — outside confirmation of a position already held, not a new idea.
- **Reversible actions get live/optimistic feedback; destructive actions require completion or confirmation.** Rauno Freiberg's "responsive immediacy" principle is close to word-for-word `CLAUDE.md`'s pre-existing rule ("Reversible actions: local-first optimistic. Destructive mutations: explicit pending state + confirmation"). This predates the research; it's independent confirmation, not a discovery.
- **Enforce good patterns with automated systems, don't rely on engineers remembering.** Shu Ding's "Performance Is Not a Technical Problem" is the explicit argument for exactly what this project's `pnpm check` / React Doctor / `/deslop` gates already do.
- **"AI slop" is specifically what craft has to differentiate against now.** Jakub Krehel uses this exact term independently of this project's `/deslop` skill name — both landed on the same word for the same problem.

## Part 2 — Worth fixing, verifying, or deciding deliberately (codebase-specific)

Every item below has been re-verified against the actual code and, where a factual library claim was involved, against real docs (2026-07-07) — not re-asserted from the original research pass. Resolved, fixed, and decided-against items have been removed entirely rather than kept as closed-out noise; what remains here are the genuinely still-open items.

- **Momentum vs. precision in drag/swipe gestures is a real judgment call, not a settled rule.** No drag/swipe gesture exists anywhere in this codebase to check it against yet — correctly a future decision, not a current one. **→ `interaction-craft`** ("Gesture engineering").
- ~~`font-body`/`font-heading` are currently the same typeface (Geist), explicitly a placeholder.~~ **Correction (2026-07-18): this is no longer accurate (and the underlying claim wasn't re-verified before this synthesis was written — an earlier draft repeated it from `michael-sommer.md` without checking).** `styles.css` defines three distinct Cal Sans faces (`Cal Sans UI`/`Text`/`Geo`) plus `JetBrains Mono`; the heading-typeface decision is already made, not pending. Michael Sommer's typography rule (pair serif+sans if combining two faces; two-of-the-same-category is the common failure mode) stays on record for any *future* font decision — it doesn't apply to this one, since it's a differentiated family rather than two similar sans-serifs.
- **Form validation feedback is color/ring-only right now** (`aria-invalid:border-destructive`, no motion) across `input.tsx`/`checkbox.tsx`/`radio-group.tsx`/`switch.tsx`/`button.tsx`. Raphael Salaja's "Exaggeration" principle (an error-field shake communicates more forcefully than color alone) is worth considering once real forms with validation exist. Deliberately not implemented blind: there's no consuming form to design the actual trigger condition against (first-invalid vs. every-keystroke vs. submit-only each have different consequences), and getting the trigger wrong risks the exact "repeated micro-interaction after first use" failure `CLAUDE.md`'s Animation Rules already ban. The principle itself is in `interaction-craft` ("Match motion intensity to what the moment needs"); applying it to these components stays open until a real form exists.

## Part 3 — Ideas worth knowing exist, for later (not urgent, nothing needs them yet)

- Fluid typography via `text-[clamp(min,preferred,max)]` for hero/display type, once a real hero exists (Guri).
- A dev-only breakpoint indicator badge, stripped from production — pairs naturally with the existing `TanStackDevtools` panel in `__root.tsx` (Guri).
- `useAnimate` + data-attribute selector orchestration for genuinely complex multi-element sequences, with a real working reference implementation already found (dimi's `animationsdev-hero` repo, `bounce.tsx`) — worth pointing at that file directly rather than starting from a simpler guide's example, if this pattern is ever needed for real. **→ `interaction-craft`** ("Gesture engineering"), the file pointer stays here since it's too specific for the skill itself.
- `useMotionTemplate` to combine multiple Motion-animated transform values (position + scale) into one owned `transform` string, for cases where splitting the concerns across two separate elements isn't an option (dimi's repo). Correction (2026-07-18): an earlier draft cited `switch.tsx` as an example of the "split across two elements" alternative — it isn't; `switch.tsx`'s thumb animates `translate` and `scale` as independent CSS properties on the *same* element via plain CSS transitions, which don't have Motion's single-`transform`-string composition problem to begin with. **→ `interaction-craft`** ("Gesture engineering").
- Idle/ambient motion (continuous subtle floating/rotation on otherwise-static elements) for anything that should feel "alive" between interactions, not just during them — not covered by any other source (dimi's repo). **→ `interaction-craft`** ("Ambient motion").
- The native View Transitions API (`view-transition-name`) for morphing between DOM states without a JS animation library — genuinely modern, needs a browser-support/SSR-hydration check before adoption, good candidate for a future image lightbox (Raphael Salaja). **→ `interaction-craft`** ("View Transitions for DOM-state morphing").
- The Peak-End Rule as a prioritization framework for where to spend craft effort once real homepage work starts — likely the hero's first seconds and whatever the page closes on, rather than uniform polish everywhere (Michael Sommer).
- Reach for real CSS Grid/subgrid once genuine layout structure exists — confirms, doesn't change, the decision already made to strip `grid-cols-subgrid` out of the adapted `SharedLayoutBackground` (Michael Sommer).
- OKLab, not OKLCH, specifically for gradients, whenever one gets added — OKLCH's circular hue can take an unexpected path between two colors (Jakub Krehel).
- Forced-state keyboard shortcuts as a debugging practice for components with several hard-to-reach edge-case states — a dev-workflow idea, not a shipped feature (Rauno Freiberg).
- Cancel an in-flight animation if a new update arrives faster than it can finish (Rauno Freiberg's 150ms threshold) — relevant once anything driven by rapid external/streaming updates exists. **→ `interaction-craft`** ("Robustness under rapid re-triggering"), generalized alongside the explicit stop-before-restart discipline from dimi's `bounce.tsx`.
- Disney's remaining under-used principles — squash-and-stretch, arcs, solid drawing via CSS `perspective` — worth knowing exist for whenever richer motion craft is wanted, none currently in use (Raphael Salaja).
- Morphing icons via a constrained 3-line SVG skeleton — bigger investment than anything else here (would mean redrawing icons, not adopting a utility), lower priority given the current fixed Phosphor icon set (Raphael Salaja).
